## 💠 O problema de criar mocks na mão

Na página anterior, criamos o mock chamando `mock(TarefaRepository.class)` direto no corpo do teste. Funciona, mas se a classe testada tem duas ou três dependências, o `@BeforeEach` fica poluído de chamadas `mock(...)` repetidas, e ainda precisa injetar cada uma manualmente no `Service` sendo testado.

```Java
// Do jeito manual
TarefaRepository tarefaRepositoryMock;
ProjetoRepository projetoRepositoryMock;
TarefaService tarefaService;

@BeforeEach
void setUp() {
    tarefaRepositoryMock = mock(TarefaRepository.class);
    projetoRepositoryMock = mock(ProjetoRepository.class);
    tarefaService = new TarefaService(tarefaRepositoryMock, projetoRepositoryMock);
    // ↑ construtor montado na mão, na ordem certa dos parâmetros
}
```

O Mockito resolve isso com três anotações que fazem esse trabalho automaticamente.

---

## 💠 `@ExtendWith(MockitoExtension.class)`

É a anotação que "liga" o Mockito na classe de teste — sem ela, as anotações `@Mock` e `@InjectMocks` a seguir não fazem nada, porque é a `MockitoExtension` quem processa elas antes de cada teste rodar.

```Java
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class TarefaServiceTest {
    // ...
}
```

Pensa nela como o "gerente de obra" da classe de teste — não constrói nada sozinha, mas é quem aciona os outros anotados abaixo pra fazerem seu trabalho antes de cada teste.

---

## 💠 `@Mock`

Substitui o `mock(TarefaRepository.class)` manual. É só anotar o campo com o tipo da dependência, e a `MockitoExtension` cria o mock automaticamente antes de cada teste.

```Java
@ExtendWith(MockitoExtension.class)
class TarefaServiceTest {

    @Mock
    private TarefaRepository tarefaRepository;

    @Mock
    private ProjetoRepository projetoRepository;
}
```

---

## 💠 `@InjectMocks`

Cria a instância da classe **testada** (não das dependências) e injeta automaticamente todos os campos anotados com `@Mock` nela — via construtor, se a classe usa `@RequiredArgsConstructor`, ou via setter, se for o caso.

```Java
@ExtendWith(MockitoExtension.class)
class TarefaServiceTest {

    @Mock
    private TarefaRepository tarefaRepository;

    @Mock
    private ProjetoRepository projetoRepository;

    @InjectMocks
    private TarefaService tarefaService;
    // ↑ o Mockito monta: new TarefaService(tarefaRepository, projetoRepository)

    @Test
    void deveBuscarTarefaPorId() {
        when(tarefaRepository.findById(1L)).thenReturn(Optional.of(tarefaFalsa));

        DadosTarefa resultado = tarefaService.buscarPorId(1L);

        assertNotNull(resultado);
    }
}
```

Não existe mais `@BeforeEach` criando nada na mão — a `MockitoExtension` resolve tudo antes de cada `@Test` rodar, com base nas anotações dos campos.

| Anotação | Função |
|---|---|
| `@ExtendWith(MockitoExtension.class)` | Ativa o processamento das anotações do Mockito na classe |
| `@Mock` | Cria um mock automático da dependência |
| `@InjectMocks` | Cria a classe testada e injeta os `@Mock` nela |

---

## 💠 Ordem de injeção importa

O `@InjectMocks` tenta casar os `@Mock` com os parâmetros do construtor da classe testada. Se o `TarefaService` espera `TarefaRepository` e `ProjetoRepository` no construtor, os dois `@Mock` correspondentes precisam existir na classe de teste — se faltar um, o Mockito injeta `null` naquele parâmetro, sem avisar erro.

Isso é um ponto de atenção: um `NullPointerException` durante o teste pode ser sintoma de um `@Mock` esquecido, não necessariamente um bug no código testado.

---

> 💡 **Resumo:** `@ExtendWith(MockitoExtension.class)` ativa o Mockito na classe de teste, `@Mock` cria as dependências falsas automaticamente, e `@InjectMocks` monta a classe testada injetando esses mocks — eliminando o setup manual do `@BeforeEach`.
