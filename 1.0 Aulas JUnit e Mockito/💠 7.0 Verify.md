## 💠 A diferença entre stub e verify

O stubbing (página 6.0) controla o que o mock **devolve**. O `verify()` faz o contrário: confirma que um método do mock foi **chamado**, sem se importar com o retorno dele.

São perguntas diferentes sobre o mesmo mock:
- Stub responde: "quando isso for chamado, o que devolver?"
- Verify responde: "isso realmente foi chamado?"

Isso importa principalmente pra métodos que não devolvem nada relevante pro teste — como `save()`, `delete()` — onde o que interessa não é o retorno, é confirmar que a ação aconteceu.

---

## 💠 `verify()` básico

```Java
@Test
void deveSalvarTarefaAoCriar() {
    Tarefa tarefaNova = new Tarefa(null, "Nova tarefa", ...);

    tarefaService.salvarTarefa(tarefaNova);

    verify(tarefaRepository).save(tarefaNova);
    //     ↑ confirma que o save() foi chamado com esse argumento específico
}
```

Se o `Service` não chamar `tarefaRepository.save(...)` em algum ponto do método, esse `verify()` falha — mesmo que nenhuma outra assertion do teste tenha reclamado de nada.

Pensa nisso como conferir se um funcionário realmente enviou o e-mail que disse que ia enviar — não importa o conteúdo do e-mail, importa que ele foi enviado.

## 💠 `times()`

Confirma **quantas vezes** um método foi chamado. Por padrão, `verify(mock).metodo()` já assume `times(1)` implicitamente.

```Java
@Test
void deveValidarUsuarioApenasUmaVez() {
    usuarioService.cadastrar(dadosUsuario);

    verify(validadorService, times(1)).validar(dadosUsuario);
}
```

```Java
@Test
void deveNotificarTodosResponsaveisDoProjeto() {
    projetoService.notificarAtraso(projetoComTresTarefas);

    verify(notificacaoService, times(3)).enviar(any());
    //                          ↑ espera exatamente 3 chamadas
}
```

## 💠 `never()`

Confirma que um método **nunca** foi chamado. Útil pra garantir que um fluxo de erro não executa uma ação que só deveria acontecer no caminho de sucesso.

```Java
@Test
void naoDeveSalvarQuandoValidacaoFalha() {
    when(validadorService.validar(dadosInvalidos)).thenReturn(false);

    assertThrows(ValidacaoException.class, () -> {
        usuarioService.cadastrar(dadosInvalidos);
    });

    verify(usuarioRepository, never()).save(any());
    //                        ↑ confirma que o save() nunca rodou, já que a validação barrou antes
}
```

Esse é um caso onde `verify(..., never())` prova algo que nenhuma outra assertion provaria — o teste podia passar só confirmando a exceção, mas sem essa linha não teríamos certeza de que o método parou **antes** de tentar salvar.

| Verificação | O que confirma |
|---|---|
| `verify(mock).metodo()` | Método foi chamado exatamente 1 vez |
| `verify(mock, times(n)).metodo()` | Método foi chamado exatamente `n` vezes |
| `verify(mock, never()).metodo()` | Método nunca foi chamado |

---

## 💠 `any()` como argumento coringa

Quando não importa o valor exato do argumento — só que o método foi chamado com algum argumento daquele tipo — usa-se `any()` (ou `any(Classe.class)`, se precisar ser mais específico sobre o tipo).

```Java
verify(tarefaRepository).save(any(Tarefa.class));
// ↑ confirma que save() foi chamado com QUALQUER Tarefa, sem verificar os campos
```

---

> 💡 **Resumo:** `verify()` confirma que um método do mock foi chamado — `times(n)` conta as chamadas, `never()` garante que não aconteceu nenhuma, e `any()` serve como coringa quando o argumento exato não importa pro teste.
