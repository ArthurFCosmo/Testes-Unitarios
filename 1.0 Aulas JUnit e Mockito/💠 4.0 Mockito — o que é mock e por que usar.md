## 💠 O problema de testar um Service sem mock

Seus `Service` no SGP dependem de `Repository` — o `TarefaService` depende de `TarefaRepository`, por exemplo, via injeção de construtor. Se você tentar testar o `TarefaService` sem mockar nada, o `TarefaRepository` real precisa existir de verdade, o que significa subir o Spring context inteiro e conectar num banco de dados real.

Isso quebra a ideia de teste unitário da página 1.0 — deixa de ser rápido e isolado, e passa a depender de o banco estar disponível, com os dados certos, na hora certa.

```Java
// Sem mock — o TarefaRepository real precisaria existir
@RequiredArgsConstructor
public class TarefaService {
    private final TarefaRepository tarefaRepository;

    public DadosTarefa buscarPorId(Long id) {
        Tarefa tarefa = tarefaRepository.findById(id)
            .orElseThrow(() -> new ElementoNaoEncontradoException("Tarefa não encontrada"));
        return converterParaDTO(tarefa);
    }
}
```

Pra testar só a lógica desse método — o `orElseThrow`, a conversão pro DTO — não precisamos que o `TarefaRepository` realmente busque nada no banco. Precisamos só que ele **devolva algo controlado por nós**, pra confirmar que o resto do método reage certo.

## 💠 O que é um mock

Mock é um objeto falso que imita a interface de uma dependência real, mas cujo comportamento é definido por você, linha por linha, dentro do teste. Ele não executa lógica nenhuma por conta própria — só devolve exatamente o que foi configurado.

É como um ator de dublê em cena de ação: de longe, na cena, parece a pessoa real fazendo aquilo. Mas quem está controlando cada movimento é o diretor (você, no teste). O `TarefaRepository` mockado "parece" o repository de verdade pro `TarefaService` que o está usando, mas por trás não toca em banco nenhum — só devolve o que você mandou.

```Java
TarefaRepository tarefaRepositoryMock = mock(TarefaRepository.class);

when(tarefaRepositoryMock.findById(1L))
    .thenReturn(Optional.of(tarefaFalsa));
// ↑ define o comportamento: quando chamarem findById(1L), devolve isso aqui
```

## 💠 Por que o Mockito

Criar mocks na mão, implementando a interface manualmente, seria muito verboso — teria que escrever uma classe fake pra cada `Repository`, sobrescrevendo cada método. O Mockito faz isso de forma automática: gera o mock em tempo de execução, sem você precisar escrever a implementação falsa.

```Java
// Sem Mockito — você mesmo implementaria a interface inteira
class TarefaRepositoryFalso implements TarefaRepository {
    @Override
    public Optional<Tarefa> findById(Long id) { ... }
    // e todos os outros métodos da interface, mesmo os que o teste não usa
}

// Com Mockito — uma linha
TarefaRepository tarefaRepositoryMock = mock(TarefaRepository.class);
```

O Mockito também controla **verificações** — não só o que o mock devolve, mas se um método dele foi realmente chamado, quantas vezes, com quais argumentos. Isso é assunto da página sobre `verify()`.

| Conceito | O que é |
|---|---|
| Mock | Objeto falso que imita uma dependência, com comportamento controlado no teste |
| `mock(Classe.class)` | Cria o mock via Mockito, sem implementar a interface na mão |
| `when().thenReturn()` | Define o que o mock devolve quando um método específico é chamado |

---

> 💡 **Resumo:** mock é uma dependência falsa cujo comportamento você controla no teste — o Mockito gera esses mocks automaticamente, evitando que o teste unitário precise de um banco de dados real pra rodar.
