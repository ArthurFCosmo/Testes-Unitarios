## 💠 O que é stubbing

Stubbing é o ato de configurar o que um mock deve devolver quando um método específico dele for chamado. É o "quando isso acontecer, devolve aquilo" que já apareceu nas páginas anteriores — agora com mais detalhe sobre as variações.

Sem stubbing, um mock recém-criado devolve valores padrão vazios — `null` pra objetos, `0` pra números, `Optional.empty()` pra `Optional`. O stub é quem diz ao mock "nesse cenário, quero que você se comporte assim".

---

## 💠 `when().thenReturn()`

A forma mais comum. Define um valor de retorno fixo pra uma chamada específica.

```Java
@Test
void deveBuscarTarefaPorId() {
    Tarefa tarefaFalsa = new Tarefa(1L, "Ajustar layout", ...);

    when(tarefaRepository.findById(1L))
        .thenReturn(Optional.of(tarefaFalsa));

    DadosTarefa resultado = tarefaService.buscarPorId(1L);

    assertEquals("Ajustar layout", resultado.titulo());
}
```

Repara que o argumento passado em `findById(1L)` importa — o stub só vale pra chamadas com **esse** argumento específico. Se o método testado chamar `findById(2L)`, o Mockito não encontra stub configurado pra esse caso e devolve o valor padrão (`Optional.empty()`, nesse caso).

```Java
// Stubs diferentes pra argumentos diferentes
when(tarefaRepository.findById(1L)).thenReturn(Optional.of(tarefaFalsa));
when(tarefaRepository.findById(2L)).thenReturn(Optional.empty());
```

## 💠 `thenThrow()`

Em vez de devolver um valor, faz o mock lançar uma exceção quando chamado. Usado pra simular cenários de erro — banco fora do ar, violação de integridade, e por aí vai.

```Java
@Test
void deveLancarExcecaoQuandoBancoFalha() {
    when(tarefaRepository.findById(1L))
        .thenThrow(new RuntimeException("Erro de conexão"));

    assertThrows(RuntimeException.class, () -> {
        tarefaService.buscarPorId(1L);
    });
}
```

Isso é bem útil combinado com `assertThrows` (página 3.0) — o stub cria o cenário de erro, a assertion confirma que o `Service` reage certo a ele.

## 💠 Cenário sem resultado — testando o `orElseThrow`

Um caso bem comum no SGP: testar que o `orElseThrow` do `Service` lança a exceção customizada certa quando o `Repository` não encontra nada.

```Java
@Test
void deveLancarElementoNaoEncontradoQuandoTarefaNaoExiste() {
    when(tarefaRepository.findById(999L))
        .thenReturn(Optional.empty());
    //            ↑ simula "não encontrado" sem precisar de banco nenhum

    assertThrows(ElementoNaoEncontradoException.class, () -> {
        tarefaService.buscarPorId(999L);
    });
}
```

Aqui não usamos `thenThrow()` no mock — o `Repository` real não lança exceção nenhuma, ele só devolve `Optional.empty()`. Quem lança a exceção é o `orElseThrow` dentro do `Service`, e é exatamente isso que o teste confirma.

| Stub | Comportamento simulado |
|---|---|
| `thenReturn(valor)` | Mock devolve um valor específico |
| `thenThrow(excecao)` | Mock lança uma exceção ao ser chamado |
| Sem stub configurado | Mock devolve o valor padrão (`null`, `Optional.empty()`, `0`) |

---

## 💠 Cuidado com stub de mais

Cada `when()` cria um comportamento condicional a um argumento específico. Configurar stub pra um argumento que o teste nunca usa é código morto — o Mockito, por padrão com `MockitoExtension`, avisa quando existe um stub configurado mas nunca chamado (`UnnecessaryStubbingException`), o que geralmente indica um teste mal escrito ou um `@BeforeEach` genérico demais.

---

> 💡 **Resumo:** stubbing define o comportamento do mock por argumento — `thenReturn()` devolve um valor controlado, `thenThrow()` simula uma falha, e a ausência de stub cai no valor padrão do tipo.
