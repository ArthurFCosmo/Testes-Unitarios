## 💠 Por que testar o Controller é diferente

Tudo até aqui testou métodos Java chamados diretamente — `tarefaService.buscarTarefaPorId(1L)`, por exemplo. Mas o `Controller` não é chamado assim em produção: ele recebe uma requisição HTTP real, com URL, verbo, corpo JSON, e devolve uma resposta HTTP com status code.

Testar um `Controller` chamando o método Java diretamente perderia justamente a parte que mais importa nele — se o `@PathVariable` está mapeado certo, se o JSON de entrada é desserializado corretamente, se o status HTTP devolvido é o esperado. O `MockMvc` simula essa requisição HTTP sem precisar subir um servidor de verdade na porta 8080.

---

## 💠 `@WebMvcTest`

Em vez de `@ExtendWith(MockitoExtension.class)`, o teste de Controller usa `@WebMvcTest`, apontando pra classe do Controller testado. Essa anotação sobe **só** a camada web do Spring — o `Controller`, os conversores de JSON, o `RestControllerAdvice` — sem subir `Service`, `Repository` ou conexão com banco.

```Java
@WebMvcTest(TarefaController.class)
class TarefaControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private TarefaService tarefaService;
    // ↑ o Service é mockado — o Controller não sabe a diferença
}
```

`@MockBean` funciona como o `@Mock` das páginas anteriores, mas registrado no contexto do Spring — é assim que o `Controller`, que espera um `TarefaService` de verdade via injeção, recebe um mock sem reclamar.

## 💠 Simulando um GET

```Java
@Test
void deveBuscarTarefaPorIdERetornar200() throws Exception {

    TarefaResponseDTO respostaFalsa = new TarefaResponseDTO(
        1L, "Ajustar layout", "Descrição", LocalDate.now(), null,
        "FAZENDO", null, null, 1L, "Sistema SGP"
    );

    when(tarefaService.buscarTarefaPorId(1L)).thenReturn(respostaFalsa);

    mockMvc.perform(get("/tarefa/{id}", 1L))
        .andExpect(status().isOk())
        .andExpect(jsonPath("$.nome").value("Ajustar layout"));
}
```

`mockMvc.perform(...)` monta a requisição — nesse caso um `GET` pra `/tarefa/1`. `andExpect(status().isOk())` confirma o status HTTP 200. `jsonPath("$.nome")` navega dentro do JSON de resposta e confirma o valor de um campo específico, sem precisar desserializar a resposta inteira numa classe Java.

## 💠 Simulando um POST com corpo JSON

```Java
@Test
void deveCriarTarefaERetornar201() throws Exception {

    String corpoRequisicao = """
        {
            "nome": "Nova tarefa",
            "descricao": "Descrição",
            "status": "PENDENTE",
            "projetoId": 1
        }
        """;

    when(tarefaService.salvarTarefa(any())).thenReturn(respostaFalsa);

    mockMvc.perform(post("/tarefa")
            .contentType(MediaType.APPLICATION_JSON)
            .content(corpoRequisicao))
        .andExpect(status().isCreated());
}
```

O corpo da requisição vira uma `String` com o JSON puro — o `MockMvc` simula exatamente o que o cliente HTTP mandaria. `.contentType(MediaType.APPLICATION_JSON)` é obrigatório aqui, senão o Spring não sabe como interpretar o corpo da requisição.

## 💠 Testando o status de erro

```Java
@Test
void deveRetornar404QuandoTarefaNaoExiste() throws Exception {

    when(tarefaService.buscarTarefaPorId(999L))
        .thenThrow(new ElementoNaoEncontradoException("Não foi encontrada Tarefa com o Id solicitado."));

    mockMvc.perform(get("/tarefa/{id}", 999L))
        .andExpect(status().isNotFound());
}
```

Esse teste só funciona corretamente se o `@RestControllerAdvice` do projeto estiver mapeando `ElementoNaoEncontradoException` pra 404 — e é exatamente isso que ele confirma. Se alguém alterar o `GlobalExceptionHandler` e essa exceção passar a virar um 500, esse teste quebra e avisa o problema.

| Anotação/Método | Função |
|---|---|
| `@WebMvcTest(Controller.class)` | Sobe só a camada web, sem Service/Repository reais |
| `@MockBean` | Registra um mock no contexto do Spring |
| `mockMvc.perform(...)` | Simula a requisição HTTP |
| `andExpect(status()...)` | Confirma o status HTTP da resposta |
| `jsonPath("$.campo")` | Confirma o valor de um campo no JSON de resposta |

## 💠 Unitário vs MockMvc — onde cada um entra

| Teste | O que valida |
|---|---|
| Unitário de Service | Lógica de negócio, validações, regras internas |
| MockMvc de Controller | Mapeamento de URL, serialização JSON, status HTTP |

Os dois são complementares — o teste unitário garante que a regra de negócio está certa, o MockMvc garante que essa regra está exposta corretamente pela API.

---

> 💡 **Resumo:** `@WebMvcTest` sobe só a camada web do Spring, `@MockBean` substitui o Service por um mock, e o `MockMvc` simula requisições HTTP reais — validando URL, JSON e status code sem precisar de um servidor rodando de verdade.
